The case study, NinjaToolKit v9.0.2, November 2026

A model reads the whole server.Code holds it to the evidence.An engineer decides every change.

NinjaToolKit is an audit and remediation platform for managed Windows Server estates and WatchGuard firewalls. I designed it, built it and released it. This is how it works, everything it does, and how each claim was measured.

It is private company software, so this study describes its architecture and method without its source. Every example, and every screen in the film, runs on an estate that does not exist, kept small so every step can be followed; the product was built against a real estate of 189 captured servers and 54 firewall exports.

Ryan Haig Forward Deployed EngineerAbout 26,000 words, 19 sections, 13 figuresEvery figure measured at the v9.0.2 tag
In one minute

The problem. An MSP's engineers diagnose and fix Windows servers and WatchGuard firewalls by hand, one script and one paste at a time, and the judgment lives in their heads.

What I built. NinjaToolKit v9, which I designed, built and shipped, working with Claude as an engineering partner since March 2026: an audit and remediation platform that puts a frontier model on production infrastructure without trusting a word it says. v9.0.2 is the current release.

What it does. It reads a PowerShell collector's capture of every server, every firewall's configuration export and live telemetry from its own agents into one record, and 179 deterministic checks judge all of it at no cost. Claude Opus then reads each server's entire output in one call. A second pass files that prose into typed items, and code verifies every quote against the capture and proves every script read-only before it reaches a server. Causes are weighed with Bayes' rule in code, the fixes are put in the order an engineer would work them, and each fix is written whole, with its proof and its way back, for a named engineer to approve. Two client audits render from the same record.

The key decision. I measured my first design against the way I actually work. It named the right cause, or part of it, in 24 of 50 cases; working the way I do at my desk, frontier model first, named it in 40. I rebuilt the system around that result.

The safety model. A model's words are testimony, not instructions. Code checks every quote against the evidence and proves every script read-only, and every change waits for a named engineer.

The proof. 6,145 tests passing at v9.0.2, 17 standing harnesses and a five-part release gate. A 2 hour 40 minute soak with 80,161 requests and no error. 318 of 318 audit fields held to the facts on the real model. Every element path that carries a value in 54 firewall exports, 1,923 of them, traced through the code and accounted for. Three releases in three days: every defect my own runs of the shipped build turned up was fixed with a test that fails without the fix.

The cost. A whole read of a large server costs $2.03, or $0.97 by batch. Every deterministic step costs nothing.

2Summary

The bottom line. NinjaToolKit v9 puts a frontier model to work on production infrastructure without trusting a word it says. The model reads a server's entire raw output in one call and reasons freely. Nothing in the product acts on that prose. A second pass files it into typed items, and code checks each one against the record: every quoted line is found in the capture, every script is parsed and proved to only read, every fix carries its own proof and its way back and waits for a named engineer. The result is a system that keeps the model's range and removes its authority.

Why that order matters. The first v9 design did the opposite. It filtered a server's evidence through checks and small models first, and sent the frontier model only what was left. Then I measured it. One read of one server's entire output, 2,424 records and about 224,000 tokens with no checklist in front of it, named a root cause and an order of work that 176 deterministic checks and twenty model reads of the parts had not. All 18 of the records it quoted were real. The design was turned around on that measurement: the model reads everything first, and code supports the read; code never narrows it.

What v9 adds over the shipped v8 line:

  • Agents. A small agent on each server reports health, events, the network and an inventory, and runs read-only checks it is handed. It calls out over TLS 1.3 and holds the line open. Nothing listens at a client.
  • A standing watch. The product learns what each server looks like when it is fine, measures which fields move by themselves, and reads only what deviates. A reading that leaves its baseline, or servers that go silent together, open a Job without anyone pressing anything.
  • One loop. Read the server whole, file what the read found, send its checks, read again when they return, order the fixes, write one fix whole, gate it, run it, prove it, watch it. The same loop serves one server and a fleet.
  • Both audits written by the model and checked by code. The model is given an audit's facts and nothing else, and every name and number in its prose is checked against those facts before a client sees it.
  • A firewall audit that reads the whole export. Every element path of the exports that carries a value is accounted for by a trace of the program's own code. Zones are read as the networks they hold, a first-match simulator says which rule really answers each service, and a firewall's page carries every finding and opens every count.
  • Causes weighed in code. Inside a diagnosis, a belief over the possible causes is updated by Bayes' rule, the next check is the one worth the most information for its cost, and a cause is confirmed only on a real proof.
  • Documents held to their facts. A Job's time entry, client email and report are checked by code against the Job's own record before an engineer copies them.
  • A real operating envelope. Sign-in by name, roles, two-person approval where an office wants it, nightly backups with a second location, a support file an engineer can send, and every model call priced before it is sent and written to a ledger.

How I know it works. Section 14 has the full account. The short version: the suite, the harnesses and the gate are green on the release commit; the program was soaked, loaded, killed mid-write and walked from an empty folder at four screen widths; and the evening v9.0.0 was released I ran it end to end with the real model on the invented estate. That run, and the filming that followed it, found four defects no test had caught. They were fixed, each with a test that fails on v9.0.0, and shipped as v9.0.1 the next morning. Filming v9.0.1 found one more, and checking the Job's documents two more; all three were fixed in v9.0.2 the day after, with the firewall pillar completed and 6,145 tests green. A release process that finds its own defects within hours is the point of having one.

3The problem, and the constraints that shaped the design

3.1 The work as it is actually done

A managed service provider looks after other companies' servers and firewalls. The engineering work has a shape that any senior engineer will recognize:

  1. Something is wrong, or might be. An alert fired, a user complained, or an audit is due.
  2. The engineer collects evidence: a script run through the remote monitoring tool, a configuration export, an event log.
  3. They read it. This is where the skill is: knowing that a clock seven minutes ahead on a branch domain controller explains the Kerberos errors on the file server next to it, and that the Group Policy failures are the same fault a third time.
  4. They write the next script to confirm it, run it, read the result, and repeat until the cause is settled.
  5. They make one change, prove it worked, write down how to undo it, and write it up for the client.

Steps 2 to 5 are where a model can help, and where an unsupervised model is dangerous. I had already been doing this work by hand with a frontier model in a chat window: paste the whole output in, ask what is wrong, take its script, run it, paste the result back. It worked well. It also depended entirely on me noticing when the model was wrong, and it left nothing behind: no record, no audit trail, no second engineer able to pick up where I stopped.

NinjaToolKit is that loop turned into a product, with the judgment that used to live in my head moved into code.

3.2 The constraints

Each of these came from the people who would use it, and each one removed easy options.

Constraint What it forced
It must run as one self-contained program. No cloud service to stand up, no dependency to install, nothing fetched at run time. A single-folder build with everything inside it, including a local model. A check at build time proves the program opens nothing outside its own folder and its data folder.
Client data is confidential. A name map that replaces every client, machine, domain and user name with a stable stand-in before text goes to any hosted model outside the primary provider. Web search is off per question and never sees a capture. Credentials are scrubbed from every string bound for a log or a page.
No change to a client's server without a named engineer's approval. Every fix waits at a gate. The gate is a table in code, never a question put to a model. An office can require two engineers. Changes through agents are off until the office turns them on.
Nothing may listen on a client's network. The agent only calls out. Work for it rides back on the answer to its own report.
The engineer is the customer. They are busy, skeptical, and will stop using anything that wastes their time or lies to them once. One act per screen. Every finding names its entity and the lines it rests on. "Cannot be determined" is a legal answer and is never drawn as a pass. Nothing explains the platform to the person using it.
Money is real. Every model call is priced before it is sent, held under a ceiling of $3.00 a question and $8.00 a run, and recorded. The AI is off in a new install. Background work spends nothing until a budget is set.
The tool must be honest about its own instrument. Absence is never rendered as zero. A count read from an event log that only holds a few hours says so. A finding that disappears is never called fixed unless a remediation is recorded against it.

3.3 Four invariants

These hold on every surface and every report, and tests enforce them.

  1. Evidence first. A screen or a report renders named entities; counts are derived on top of them and every count opens its list.
  2. Comprehensiveness. A firewall audit is everything behind the firewall. There is no "top ten".
  3. Granularity preserved. Every field the collector captures survives ingest, storage, judgment and rendering.
  4. A commercial boundary. A client-facing document carries no pricing or cost content.

4The system in one picture

Reading the picture. Four kinds of input land in one record through one reader each. Deterministic checks judge everything first, at no cost. The model then reads each server whole, with the checks' findings beside it as context and never as a filter. Filing turns the read's prose into typed items that code can verify. Verified checks go to the server and their output comes back to a second read. Findings are placed into a kept list of fixes, the list is ordered the way an engineer would work it, and one fix at a time is written whole and brought to a person. An approved fix runs through the same agent, and its proof is a measurement taken later from outside the change.

5.2 The capture: from a wall of text to a server's record

A fleet run through the monitoring tool returns one paste holding every machine's console output under a header line of its own. The splitter recognizes that wrapper, strips it, and keeps each machine's header, site and run status for ingest. Each machine's block is then cut into its 47 sections and each section goes to its own parser: identity, hardware, storage, the operating system, roles, Active Directory, DNS, DHCP, file services, IIS, SQL Server, Exchange, Hyper-V, installed software, services, the network, security settings, scheduled tasks, backup, event logs, permissions, certificates, Group Policy, encryption, protocols, processes, and the rest.

Three decisions here pay off everywhere else:

  • The raw text is kept beside the parse. The parse serves the checks and the pages. The raw text is what the model reads, exactly as it came (section 9.4).
  • A stored parse carries the fingerprint of the parser that made it. When the parser changes, a stored parse made by older code is parsed again on first use. Nobody re-ingests, and no page ever mixes two parsers' ideas of a server.
  • Each server is saved in its own short write as it is read. A capture of an entire fleet appears on the pages server by server while the drop is still being read, and no other engineer waits behind it. The drop is a batch with a state of its own (open, grouping, done, refused, interrupted), so a process that stops mid-drop says exactly what landed.

Agents and the newer collector emit typed records instead of text: one JSON record a line under a fixed envelope (schema, run, token, host, sequence number, section, kind). A run is whole only when it has a begin record, an end record whose count matches, and no gap in the numbering. A run that is not whole is kept and says why; it is never silently treated as complete. A bridge writes a typed run back out in the text collector's own layout, so every parser, check, page and audit works on both shapes.

5.3 Who is who

A server goes by several names: the roster's device name, the capture's upper-case host name, its fully qualified name, and its 15-character NetBIOS name. The matcher places each one under its client from evidence, rung by rung, and records which rung placed it and on what evidence. Where the evidence ends, or points at two clients, it places nothing and asks an engineer once; the answer is kept and never asked again.

Two rules in this matcher were learned from measurements, and both are refusals:

  • An address never places anything. Private address ranges repeat across clients. Measured against the real estate: joining firewalls to clients by subnet split on 32 of 37 exports and named the wrong client on 6. Joining by directory domain placed 13, and all 13 were right.
  • A firewall is never linked to a client by a guess. An export's file name is whatever an engineer typed. A firewall belongs to the client an engineer links it to, and until then its audit names no server.

Findings have identity and history. A finding is the same finding next time by what it is about, never by its position in a list or by a model's wording. When a new capture is laid over the last one, each finding is opened, seen again, or gone, and a finding that is gone is classified by why it is gone. The word "closed" is refused for anything no remediation is recorded against. This one rule is what lets the product claim a fix worked: the claim rests on a recorded change and a later measurement, never on an absence.

5.5 The dependency map and the seams

Two derived structures turn a list of servers into an estate.

The dependency map records what each server leans on, and each link carries its evidence: the domain controllers of its domain (from a captured controller's own directory), the DNS servers its adapters ask, its DHCP server, its Hyper-V host, the file servers it holds open connections to, its network on the client's linked firewalls, and its backup server. An address resolves to a server only when a captured server of the same client holds it. Where the records end, the link says so with the reason.

The seams are where one client's facts disagree across its servers. Every fact several servers hold about the same thing is lined up: an address and who holds it, what each DNS server answers for a name, each server's time source, its gateways, a Group Policy's version as each controller sees it, where each virtual machine runs. Where two sides disagree, the seam keeps both and where each came from. No rule names a problem here. A seam is a disagreement to explain, and it is some of the best material the model is ever given.

The instrument's own traps are checked before anything is marked: a MAC address is one value however it was written; a MAC that one server sees at many addresses is a router's and places nothing; a policy version the collector could not read is not a disagreement; a side with nothing captured is missing, never different.

5.6 Reference knowledge as dated data

Facts that go stale are data files, never code: the Windows Server, SQL Server and Exchange lifecycles with each Extended Security Update year, firmware release dates, the snapshot of known-exploited vulnerabilities, Microsoft's security baseline (361 settings, each with its expected value by server role), NIST's control catalogue and the CSF core. Each file carries where every fact was read, the date it was read, and a stated life in days. A file read longer ago than its life fails the test suite and the build, so the source is fetched again before the product can ship.

6Deterministic first: the check catalogue

A model should never be asked a question that code can answer exactly. Before any model call, 179 deterministic checks judge every server and every firewall. They cost nothing, they run in under a second a server, and they are the floor the product stands on with the AI switched off.

6.1 One contract for every check

Every check, whether it reads a disk's free space or a domain's delegation settings, takes the same shape. It declares what it reads, when it does not apply and why, and it answers with exactly one of four outcomes:

Outcome Meaning
A fault Something is wrong, with the exact values it decided on
Healthy Checked, and fine. A legal answer, shown as one
Cannot be determined The capture does not hold what would decide it. Said with what would. Never scored as a pass
Not applicable The subject is not the kind of thing this check judges, with the reason

A fault also carries the conditions that would make it acceptable, each phrased as a question for the client. "This share grants Everyone full control" is a fault; "it is a scanner drop that holds nothing for more than an hour" is a condition that an answer can cross off. This is how an engineer teaches a junior to read a finding, and it is what stops a tool from crying wolf.

Every check ships with labelled examples and must pass a proof of its own contract before it may join the catalogue.

6.3 Instrument honesty

A check that counts events is only as good as the log it counts from. On the real estate, the Security log held less than the seven-day window the checks read on 95 of 179 servers, and less than a single day on 43, some of them only minutes, because a 20 MB log was being filled by object-access auditing. A count read from such a log is a floor, and a zero is not a quiet week. So one check names every log that is too small, and every check that counts from a log says how much of the window that log actually held.

The same discipline applies to the agent. An event a server does not audit is reported as "not audited here", never as zero, because the agent sends each server's effective audit policy with its counts.

6.4 One change fixes many servers

Findings are not work. Changes are. Measured on the estate: 2,116 findings on 189 servers came from 54 distinct checks, and 91% of them from 35 checks that each fired on 20 servers or more. A pattern is one client's servers carrying one check's finding where the change that closes it is made once for all of them: one Group Policy, one policy in the endpoint product's console, one script. The product groups them, diagnoses the pattern once, and confirms each server from its own evidence. Where every server shares one cause, code alone settles it, at no cost.

6.5 Compliance, control by control

Findings map to NIST SP 800-53 Rev 5's Moderate baseline, 287 controls, read from NIST's own machine-readable catalogue. Every control is in exactly one of four states:

NIST CSF 2.0's 106 subcategories follow from the same controls through the references NIST itself publishes. A scanner that reports "94% compliant" from configuration alone is overclaiming, and an auditor will know it. This one does not.

7The firewall pillar

The firewall half of the product is a network engineering tool in its own right. It reads a WatchGuard Firebox's configuration export and answers the questions an engineer would spend a day answering by hand in Policy Manager: what does this box let in, from whom, to which machine, and does anything actually answer there?

7.1 One model, read twice

The export is read into one firewall model: the device, its interfaces, address groups and aliases, services, policies in their order, static and dynamic NAT, IKE gateways and tunnels, Mobile VPN, users, authentication domains and licences. Lists keep the export's order. An absent value is absent, never a made-up default.

Every later judge, page and audit reads that one model, so the screen and the client's audit cannot disagree about a number. Two independent readers fill it, and a standing test holds them in agreement over every export the product was built against.

The export is read in full, and that is measured, not believed. A ledger lists every element path the 54 exports contain. A tool traces the program's own code, as the firewall's page and audit run it, to find which of those paths it actually reads, and writes the answer into the ledger. When it first ran, 341 of the 1,923 paths that carry a value were read. The next day every one was accounted for: 1,531 read and stated in the audit's chapters and on the firewall's page; 23 secrets, said as set or not set and never shown; and 369 that are not part of an audit, each with its reason (radio tuning, display settings, the text of a proxy's deny page). Tests hold it as a measurement: every status carries its reason, what is left to read may only fall, what the code reads is what the ledger says it reads, and no secret reaches any copy of an audit or what a page is sent. An export that carries a path nobody has read is named instead of silently skipped, and the audit's scope chapter says what it read of the export in front of it.

Small things matter in this parser, and each one below was a real defect before it was a rule:

  • A policy's number is Policy Manager's number. On the real exports, 1,428 of 1,505 policies sit at a different place in the file than the number Policy Manager shows, by 1 to 10, because the file also counts the Firebox's own hidden policies. An engineer told to edit "policy 14" must land on the right one, so the product carries Policy Manager's number and never the file position.
  • VPN cryptography is not where it looks. Phase 2 lives in sibling elements that name the IKE policy they serve. A proposal with a self-describing name states its algorithms; a hand-named one is decoded from its numeric fields.
  • Where an address leads is judged from the box's own interfaces, never from how the address looks. A public-looking network that sits on a trusted interface is inside. A branch tunnel is a branch, never the internet.

7.3 Posture a reader can explain

Every firewall check belongs to one of five domains: what answers the internet (Exposure), who gets in and how (Access), what the Firebox looks inside (Inspection), the tunnels (VPN), and keeping the box (Operations). A rule that fired costs its points in its domain. A domain scores 100 less its points. The posture is the worst domain, which tells the reader why in one word. Only faults count: an affirmed control, an undetermined answer and a not-applicable one cost nothing. Each finding also carries its MITRE ATT&CK technique and tactic, with revoked techniques mapped to the ones that replaced them.

7.4 Exposure is a path, not a port

This is the pillar's center. A port scan tells you a port is open. An engineer needs to know what the open port reaches.

A path runs from the internet through a firewall's static NAT and the policy that carries it, past its gate, to an internal address and port, and on to the audited server that holds that address and whatever listens there. The firewall's half comes from the rule base. The server's half comes from the captures. The join is computed once, and the Paths page, the server's page, the firewall's page and both audits all read the same rows.

The gate is decided by the policy's weakest source member: a policy that names a user group beside "any external address" admits anyone. Every path ends in one of six states:

State Meaning
Live A server at that address listens on that port
Not listening The server is there, its capture lists its listeners, and none is on that port. The route publishes nothing that answers: an orphan to remove
Listeners not collected The server is there; its capture holds no listener table
Ambiguous More than one of the client's servers holds the address. Kept as ambiguous, never resolved to a guess
No host None of the client's audited servers holds the address
Elsewhere Only another client's server holds the address

That last state exists because of a real false alarm. Matching by address alone once reported a domain controller published to the internet. The controller belonged to a different client that happened to use the same private range. The join is now constrained by client, and the near miss is kept and shown as exactly that.

A second step follows each live path: what the exposed host may reach next, from the rule base's allow rules between zones. That is what turns "port 3389 is open" into "the internet reaches a session host that can reach the domain controller", which is the sentence that gets a change approved.

7.5 Reading a rule base the way a policy analyser does

The rule base page names five kinds of anomaly, pair by pair: a shadowed rule (an earlier rule takes all of its traffic and acts differently, so it never fires), a redundant one (an earlier rule takes all of it and acts the same), a generalization (a later, broader rule acts differently, so the narrow one is an exception above it: usually meant, reported for reading), a correlation (two rules that act differently each take part of the other's traffic, so their order decides), and a consolidation (two rules that could be one).

The comparison is made on the address space each side resolves to, the user groups that confine it, the interfaces an "any" is held to and the rules' schedules. It is never made on alias names, because this vendor names every policy's aliases after the policy, so names almost never match. A claim is made only where both rules' coverage is proved; an unresolved side is no claim. The analyser under-reports and never invents. One reading was tried and thrown out on measurement: treating two policies that differ only in service as a consolidation named 196 pairs across 37 exports, a fifth of some rule bases, and not one was a finding. On this platform a policy is one policy type, so that is simply how a rule base is written.

Zones are read as the networks they hold. A WatchGuard rule names a zone, "Any-Trusted" or "Any-Optional", where another vendor's would name an address. Read as a name, a narrow rule beneath a broader one on the trusted network was invisible to the analysis. A zone is now the networks the export says it holds: its enabled interfaces' networks, the static routes through a gateway on them, the SSL VPN and Mobile VPN pools, each branch tunnel's remote networks and the routes over its virtual interfaces. Containment is read in one direction only (a /24 takes a host inside it, never the reverse), so the analysis can under-report and never invent.

Which rule really answers. For every service a policy names, the analysis states the first enabled policy that takes it, by the addresses each side resolves to, numbered as Policy Manager numbers it: 899 rows across the 37 devices. Where the policy that names a service never runs because an earlier, broader one takes its traffic, the row names the earlier policy and the one it takes the service from; on 4 devices, 6 rows do.

7.6 Tunnels, certificates and firmware

Each tunnel's cryptography is graded from the weakest Phase 1 transform and Phase 2 proposal a peer may negotiate. The Firebox's own certificates are judged at the date the configuration was saved, since an expired web-server certificate is what breaks the management page and the SSL VPN portal for users. Firmware is compared against the newest build on its own release line and against a bundled snapshot of vulnerabilities known to be exploited, and the finding says how old that snapshot is.

The tunnel tables and the VPN finding share one grading. Measured on the 165 IKE policies across the 37 devices, an earlier table graded by rules of its own and showed a worst cell different from the finding's grade on 25 tunnels. Each proposal is now coloured part by part by the finding's own grading, against both standards the finding cites; the worst cell is the finding's grade on all 165, and a test holds the two together over every mix of proposals, 2,880 of them.

7.7 From a finding to a change made by hand

A firewall's fixes are never pushed. An engineer makes them in Policy Manager or the Web UI, and the product's job is to make that safe and provable:

  • A firewall Job is written from the engine's findings on the stored configuration: one issue per change.
  • Each written step names only what the firmware has. Menu paths in a step are looked up in a vocabulary read from the vendor's own documentation, so a step never sends an engineer to a menu that does not exist.
  • The proof is the next export. After the change, the engineer saves the configuration again and drops it in. "What changed" compares the two models and shows the before and after; the finding is closed by that evidence.
  • Complaints are worked by code first. A site blocked, an inside service unreachable, a branch tunnel down, remote users dropping: each family's first checks read what is already held (the model, the rule base, the logs) before any model is asked, and a tunnel is diagnosed from both ends when both Fireboxes are in the record.

7.8 Linking the two pillars

When an engineer links a firewall to its client, the two halves of the product join. The firewall's ways in gain the servers behind them. A server's page shows what the internet reaches on it. The site audit's network chapter draws the firewall's routes onto the servers' network. And a check on the server side reads the same exposure rows, so a server with Remote Desktop published to any address is a finding on the server, on the firewall, and on the path between them, counted once.

7.9 A firewall's page carries everything its audit does

A firewall's page is a working dashboard, not a summary of the audit. Until v9.0.2 it listed six findings a chapter, and measured across the 37 firewalls, 350 of 1,155 findings were only in the printed audit. Each chapter now lists all of its findings, each opening in place to its evidence, its steps, its proof and its way back.

  • Every count opens its list. Each of the 24 figures on a firewall's opening (findings, posture, ways in, rules, tunnels, services, licences) opens the named rows behind it in place, with a way to the chapter that holds them.
  • What was missing is carried. The services and aliases an engineer made that nothing uses; the Firebox's user groups, with the users authorised one by one for rules listed apart from them; the networks behind each dynamic NAT rule; the proxy actions' inspection, policy by policy.
  • Secrets are stated, never shown. A password, a pass phrase, a pre-shared key or a shared secret is said as set or not set.
  • Ask about anything. Each policy, finding and section carries an Ask that opens the console on that firewall with the item already named, the question left to the engineer.

The page and both copies of the audit read one set of sections from the audit's model, so a figure cannot appear on one and not the other.

8Agents and the standing watch

A capture is a photograph. An estate needs a pulse. v9 adds a small agent on each server and a standing watch in the office that reads what the agents send. This section is systems administration and security engineering: a program that runs as SYSTEM on a client's server has to be boring, careful and impossible to turn against its host.

8.1 The agent

The agent is its own build, with its own small code base, installed as a scheduled task under SYSTEM. Its design is a list of things it does not do:

  • It starts no other process to take a reading. Health, events, the network and the inventory are read through the Windows API directly: processor time, memory, disks, services and their start types, a pending reboot, the event log API, the audit policy API. There is no PowerShell child for an endpoint protection product to stop, and no command line to tamper with.
  • It never reads an event's text or a secret. Events are counted exactly, by log, provider, event ID and level, with the first and last time of each.
  • It listens on nothing.
  • It never adds to a host's trouble. When the processor was busy at the last reading, the heavier reads wait.
Reading Cadence Notes
Health Every 5 minutes Processor, memory, fixed disks, uptime, automatic services not running, a pending reboot
Events Every 10 minutes, each log Window after window with no gap, from where the last one ended
Network Hourly Addresses, DNS servers, TCP listeners
Inventory Daily Operating system and build, domain, hardware, installed software, plus 30 further reads the text collector cannot take: disk provisioning, a volume's dirty bit, adapter settings and more

Records are held on disk until the office confirms it has them. Each batch is one file, written whole under a temporary name and then renamed, so a power cut never leaves half a batch. Batches go oldest first. One the office refuses is set aside with the reason and never blocks the ones behind it. Through a long outage the queue keeps its newest data up to a size limit and counts what it dropped.

8.2 The line

The office application runs its own small certificate authority. The install code an engineer downloads for a client carries the SHA-256 fingerprint of the listener's certificate. The agent connects, checks that fingerprint before it says anything, and only then sends its single-use code and a certificate request made with a key generated on that server. From then on, both ends prove themselves on every connection. An agent is known by the fingerprint of its certificate, and a revoked one is refused at the next request.

The listener is a separate server on its own port. It is never the console, and it answers exactly three things: an enrolment, a batch of records, and a ping. Work for an agent travels on the answer to its own report. The agent calls out, keeps the line open, and asks again shortly while a check is on its way. Nothing at a client's site ever accepts a connection, so there is nothing there to scan, and no inbound rule to ask a client's firewall for.

The listener also defends itself: a rate limit by address, a bounded worker pool, and one short write a batch. Fifty agents reporting for an hour put 650 batches in and 650 readings were kept.

8.3 Rules, alerts and Jobs

Only deterministic rules raise alerts. Each rule reads one server's recent readings, its event windows, how long a reboot has waited and when its agent last reported. It says what is wrong in the server's own figures and what an engineer does first. A rule that cannot be judged from what has arrived stays quiet instead of guessing. One alert is kept per server and condition: opened when it first holds, kept current while it holds, closed after a quiet hour.

Between an alert and a Job sit layers that keep the noise out, cheapest first:

  1. Code, free. An alert that fired just after its server restarted is held and read again once the server has settled, because a symptom that only follows a restart is not a fault. One that keeps firing joins the Job it already opened.
  2. Grouping by evidence. Servers that go silent together are one problem, and one Job: three branch servers dropping off at the same minute is a link or a host, not three incidents. A problem joins another server's only through an edge of the dependency map.
  3. The decision model, only inside a budget. A condition known to be harmless on a server like this one is kept and said, never opened, and only when the model's answer is inside its fitted bound.
  4. A nightly review. A rule that fired repeatedly and was held or judged harmless every time is proposed for quieting on that one server, for an engineer to confirm.

What is still new opens a Job in its client's work, with its issues written by code. Its diagnosis starts by itself only while that client has budget left for a whole run. With no budget set, the Job waits for an engineer.

8.4 The watch: learning what "fine" looks like

The hard problem in watching a fleet is that almost everything differs between two looks at the same healthy server: process IDs, counters, memory figures, last-run times. Read naively, every server is always changing. The usual answer is a hand-written list of fields to ignore. That list is never finished and is wrong on the next product a client installs.

The watch measures instead.

Which fields move by themselves. The product takes pairs of captures of the same server, matches each record with itself, and records which fields differed together. A field is called moving when it differed often enough to say anything, it takes many values across the fleet (a field with few values is a state, and a service that keeps stopping is a finding however often it flips), and when it differed it mostly differed alone. A field that changes together with the rest of its record is the record changing. A moving number whose changes are mostly small is a level, and the band it drifts within is kept: an event counted ten times more often than usual has left its band, and that is a change.

The instrument's own shifts. A time that moved by the same amount on many records of one capture is the collector's doing (a daylight-saving change moves every timestamp by an hour), and is read as unmoved. A time that moved by anything else is a real change: someone edited a Group Policy.

Which kinds are streams. A kind of record most of whose keys were not there at the last look (recent events, short-lived ports) is a stream, where a new record is the kind doing what it does.

What many servers say alike. A record's form is what it says with its moving values set aside. Across the real fleet, only three records in ten are distinct. One look at a form can serve every server that carries it, though being common is never a verdict: every server of a client can carry the same fault.

With those measured, every record of a new capture is given one standing:

Standing Meaning What happens
Deviates It was accepted in one form and now stands in another Read first
Changed Never accepted, and it differs from the last look in something that does not move by itself Read
New Not there at the last look (or flow, when its kind is a stream) Read, unless it is a stream doing what streams do
Unread The same as before, and nothing has ever looked at it Left for the digest
Rests Accepted, and it still stands as accepted Taken out of the work, while it holds
Gone The last look held it and this capture does not Explained, never assumed fixed

Two properties of this table carry the design. Only "rests" leaves the work, and only while it holds. And not having changed is never acceptance: a record nobody ever looked at stays unread however long it has stood. The baseline never narrows what can be found. It only stops the same settled thing from being graded again every night, and it makes a change in a record nothing ever flagged stand out.

Measured on the estate, this funnel drops 92% of records between two captures of the same server before any model sees them, and loses none of them: every record stays in the capture, on the map and in every whole read.

8.5 A round of the watch

For a client the watch is switched on for, inside that client's daily budget:

  1. A look at each server that moved. What deviates, changed, is new or is gone is woven into small groups of records that are provably about the same thing (a service named in an event's message; two records naming the same other machine). The decision model grades every line, a dozen at a time: fault, routine or unclear. The large model then reads what climbs, the server's changes whole, because changes that arrive together usually have one cause. The small model earns its seat here slowly, and on purpose. Measured: asked to grade records that no reader had seen, 7 of its 40 most confident "routine" answers were faults. So until an office's own labels fit a line for this question, its answers are recorded and everything still climbs. It works in shadow, and the frontier model's reading is its teacher.
  2. The digest of what nothing has looked at. After a first read, about 85 records in 100 had still been looked at by nothing. The digest works through them by form, so the same words are never put to a model twice.

A look is finished only when every part of it was settled. A look that was cut short, or whose model did not answer, leaves the server exactly as it was: everything that moved is still moved at the next round. A finding lands on its server; a line found fine is accepted on that server; a question only a person can answer is asked once and its answer is kept as a fact about the client.

The watch is asked for, client by client. No client is watched until an engineer turns it on, because its first round reads everything that client's servers hold and spends against that client's budget.

8.6 Proof after a change, and the daily clean read

A fix's own script checks itself just after it runs. That is not the proof. The proof comes later and from outside the change: the fix's fingerprint, a read-only test that is true while the problem exists, is run again on the server through its agent once the change has settled; and the record's watch on the findings that fix settles is compared against untouched servers that hold the same finding over the same window. The control group shows that the reading still sees the condition where nothing was changed. Both hold, and the fix is verified with its before and after kept. Either fails, and the fix has failed: a reversible fix has its way back sent the same way the fix went, and anything else asks an engineer.

Once a day, outside a client's quiet hours, each server with an agent gets one read-only sweep of the fingerprint of every fix applied there recently. A clean result is kept as a clean day. This is how an experienced engineer closes an engagement, by re-running the consolidated sweep until it reads clean, made continuous.

9The harness

The harness is everything between a model and the world: what the model is shown, how it is asked, what is done with its answer, what it may cause, what it costs, and how the whole thing gets better with use. It is the part of this product I would defend line by line, and the part most worth reading if you build with frontier models.

Its one rule: a model's words are testimony, not instructions. Nothing in the product executes, files, closes or changes anything because a model said so. Every effect passes through code that checks the claim against evidence the model did not write.

9.1 The measurement that turned the design around

The first v9 harness was a ladder I called the burn-down. Each question climbed from the cheapest rung that might settle it to the most expensive: code, then a local reader of names, then a calibrated decision model, then a check on the machine, then the frontier model, then the engineer. The frontier model saw only the residue. On a simulated estate it was cheap and precise.

Then I replayed real diagnostic cases through it and compared it with how I actually work a server with a model at my desk: one conversation, the whole output pasted in, a best guess every turn.

The ladder (frontier model last) The desk loop (frontier model first)
Named the right cause, or part of it, on 50 scored cases 24 40
Policy on uncertainty Name a cause only when sure Give a best read every turn and say how settled it is
"Settled" wrong n/a 1 time in 30
Cost baseline about half

The ladder had been muzzling the model. Asking it to speak only when certain made it silent exactly where a hypothesis was most useful. And filtering its input through checks meant it never saw the two unrelated-looking lines, 1,900 records apart, that together named the root.

The measurement that settled it: one read of one real server's entire raw output, 2,424 records and about 224,000 tokens, with no form to fill and no checklist. It named a root cause and an order of work that 176 deterministic checks and twenty reads of the parts had not. Every one of the 18 records it quoted was real.

So the design was inverted, and the ladder was kept for what it is good at. The frontier model reads everything first. Code and the small models then do what they are measurably right at: verifying, placing, grading and remembering. The engine that climbs rungs is still the engine. What changed is which questions are put to it.

9.2 The engine: runs, questions and rungs

Every unit of AI work is a run: a server's whole read, its filing, a watch round, a firewall's diagnosis, an audit's prose, a console turn, a fix being written. A run sets out to settle questions. Each question climbs rungs, cheapest first, and a rung says exactly one of three things:

Answer Meaning
Settled Here is the answer, its confidence and its proof
Climb I cannot settle it; here is what I learned; the next rung should try
Hold I am waiting for something outside the run: a check's output, or the engineer. Named

Every try is kept as a node in a graph: what it read, what it said, its proof, its confidence, what it cost and how long it took, and the facts it produced, linked to the question, to the try below it and to the causes its claims bear on. That graph is the run's audit trail. It is also what the engine page draws, and what the learning loop measures each rung's accuracy from.

The engine holds nothing between calls. A run is read back from its record every time it advances. So a run whose process died half way resumes where it was, with whatever was in flight marked as interrupted and tried again. A run waiting on a check's output simply goes on when the output is in. And no database write is ever held open while a rung works. This is what made "kill the process in the middle of a model call" a test that passes.

Before any rung that spends, the engine asks the AI switches (the office, the function, the client) and the ceilings: $3.00 a question, $8.00 a run. A rung that is refused is recorded as skipped, with the reason, and the question climbs past it, ending with the engineer when nothing else may try.

One door for all of it. Every piece of AI work waits at one scheduler with four lanes:

Lane What runs in it
Engineer What a person started: a read, a console turn, an audit. Never behind background work, never counted against it
Gate What follows an engineer's answer: a check that came back, a fix to prove
Watch The standing watch over a client's fleet
Nightly Reviews, the fix list, the office's standard

The three background lanes share a fixed number of slots, earlier lanes first, and at most a set number run at once for any one client, so one busy client never starves the rest. That is the difference between an AI feature and an AI service several people can use at the same time.

9.3 One client for every model call

There is exactly one place in the program that calls a Claude model, and a test refuses a second. Every call through it:

  • Is refused at once while the AI switch is off. The switch is read on every call, and a missing or unreadable setting reads as off. It fails closed.
  • Is priced before it is sent. Its worst case is logged as sent, and what it actually cost, cache reads and writes included, is logged as done and written to a ledger row beside the log line, so the database and the log always hold the same calls at the same prices. If the database is busy the row is retried in the background: an early version lost 9 of 178 rows to a locked database, and a ledger that drops rows is worse than none.
  • Streams when it is long. A long call once sent whole was dropped and silently sent again by the SDK: 508 seconds across two attempts, the first never recorded. Long calls now stream, which also lets an engineer stop one.
  • Uses adaptive thinking, bounded by an effort setting, which is what current models accept.
  • Is resent once on the fallback model when the primary declines it, with both calls billed and later calls of that kind routed to the fallback first. A request is never reworded to slip past a refusal.
  • Is cut cleanly by a Stop, keeping what arrived, and is stopped by code if the reply starts repeating one short piece to its end.
  • Raises only typed errors, scrubbed of any credential, each a kind and one plain sentence an engineer can read.

Evidence that many calls share is sent as a cached prefix. Questions about one server arrive minutes apart, which is the gap an hour-long cache pays for.

9.4 The whole read

The model is given a server's entire collector output, exactly as it came, in plain words, with no form to fill and nothing filtered or judged by code in front of it, and room to think. Beside it: what the office and the client have said, what the checks already raise, and what the model itself wrote last time.

It says what the server really is, what is wrong with it by root and symptom in order, what it would do about each, what it would check next (as the read-only PowerShell itself), what only a person can answer, and what is fine. Findings are numbered, so a later look speaks of the same finding by its number.

Two things about how it is asked matter more than any clever prompt:

  • It is talked to like a colleague who has just been handed the folder. It is told where it is, whose estate this is, how the data arrived and what the work is aiming for. The more a prompt reads like a form, the more the answer reads like one.
  • It is told it is in a loop. Its checks will run and come back. A check that code can prove read-only runs by itself. Every change waits for an engineer. A reader that knows it will get another look gives its best read instead of hedging everything into uselessness.

The same step runs one level up: the model's own write-ups of each of a client's servers are read across, for what no single server shows and for the order to work in.

9.5 Filing: the bridge from prose to the record

A whole read is free reasoning in the model's own words. There are no code words in it and no hidden markers. So how does a paragraph become work? By a second, deliberately dull run called filing.

  1. The local model proposes the things the prose names: machines, accounts, services, products. It settles nothing. Its proposals climb with the question.
  2. The frontier model files its own write-up into a form, adding nothing and judging nothing new: every finding with the records it quotes, how sure it said it was, and the finding it names as its root; every check as written; every question and whose it is to answer; and a verdict on each name the local model proposed. So the small model's guesses reach the large one with their likelihood, and the large one's verdict becomes the small one's training label.
  3. Code checks what was filed, by reading and never by words. Each quoted record is looked for in the capture the read was made from. Each script is parsed and proved to only read, or the reasons it does not are kept beside it.
  4. The decision model is asked one typed question per finding: is this the same problem a deterministic check already raised on this server? Its answer is used only where it clears its fitted line (section 9.9).

Nothing is dropped for failing a check. An item is kept with what code found, so a finding whose records were not found is shown as exactly that, and never as proven.

Finding a quote is harder than it sounds

On four real reads, an exact text search found 191 of 376 quoted records. Yet every one of 18 quotes checked by hand was true. The model writes a record the way a person would in a note, not as the row stands in the file. A matcher that only does exact search would have thrown away half of a correct read. A matcher that is too loose would "find" anything. So a quote is looked for four ways, strictest first:

  1. Word for word, in a line of the capture as it came.
  2. As the row itself: the quote is a set of name and value pairs equal to a record's own.
  3. By its names and values: every name-like word of the quote sits in one record, with most of its numbers.
  4. The same, across one set of records of the same section and kind, when no single record holds them all.

What comes back is the record's place, how it was found, and on how many records it was found, so a quote that fits hundreds of rows is known to pin nothing. A quote too thin to place is not found, by rule.

9.6 Landing

Landing takes each filed finding up into the record once, by code and on typed fields only:

  • A finding that stands on records code found becomes a finding of the record, keyed by the record it stands on. From then on "its evidence still stands" is checked against the next capture like any other finding's.
  • A finding the read itself said is what a deterministic check already flags is not a second finding. Its records are kept as showing that check's.
  • A finding with no record pinned is kept as said, with why. It waits for a check to show it, and opens nothing.

Every item's place is recorded in both directions, so landing a read twice changes nothing. Idempotence is not a nicety here: reads are retried, processes restart, and a duplicated finding is a lie in a client's report.

9.7 Checks out and back

The read wrote the checks it would run next. Each must now cross three controls before it touches a server.

The read-only proof. A script runs by itself only when code proves, by parsing it, that it reads and changes nothing. First an allow-list analysis of what the script does. Then PowerShell's own parser is run over the block: every command with its arguments, every method call with its type, every property that is set, every type named, an exit, a redirection, each judged against the same allow lists. A block the parser cannot be run on is not a read. The proof fails closed.

About one check in ten that the model writes is refused, nearly always for the same few reasons: a vendor's own executable, a fetch from the network, a construct the proof cannot see through. A refused check is shown once more to the model that wrote it, with code's reasons. What it writes back is proved exactly as the first was. Proven, it takes the check's place. Not proven, the check waits for an engineer as it was first written, with both reasons. A check is rewritten once only.

One script per server. The proven checks of a server's read are joined into one script, each between its own two marks, with a failure of one printed as a line and never stopping the rest. The joined script is proved again as it will run, and a check whose addition breaks the proof is left out.

The gate hook. Every action the model proposes passes one hook before anything happens. It is code in the path, never a tool the model could decide not to call, and the model's reasoning never reaches it: the hook sees only what the action is and does. In order:

  1. Code's hard rules, never overruled. The script passed its checks. It touches only the machines its step asked about. Every line it quotes stands in the evidence it was shown. A fix always asks a person.
  2. The client's setting. An office can set any client so that checks wait for one press.
  3. A second opinion from the decision model: is the action about the Job's step, is it grounded, does it touch anything unasked. Any doubt asks the engineer. A second opinion that is set up and does not answer also asks the engineer. It is never the only control and never the reason an action runs.

The verdict is run (read-only only), hold (one press by an engineer), or refuse, each with why and by whom.

Where an agent reports from the server, the script runs through it. Where none does, it becomes one card for that server: the engineer copies it, runs it through the remote monitoring tool, and pastes the output back. The product works the same with no agents at all.

What comes back is cut at the marks and read beside each check it answers. If a script was cut short, the checks it never reached go out again by themselves. That last sentence is one of the four defects v9.0.1 fixed (section 14.5).

9.8 The second look, and questions that become facts

The second look is the same conversation picked back up: the output whole again, the model's own last write-up, what each check returned, the answers people gave, and where each finding stands now. It is the same step an engineer takes when a script's output comes back, and it is where hypotheses become settled or get dropped. A second look may quote what its checks printed, and code looks for those quotes in the checks' output and records which check printed each.

A read asks two kinds of question, and the product treats them differently:

  • What only the client can answer (is this account still used, when is the maintenance window) becomes a question for the client. Its answer is a fact about that client, read into every later call for that client.
  • What is the provider's own to answer (is this remote tool ours, how do we patch) is true for every client. It is asked once, kept once, and read into every later call for any client.

Nothing an engineer has said is ever asked again.

Weighing causes in code

Inside a Job's diagnosis, what the evidence says about each cause is a number, kept and updated by code. A belief is a probability over a family's causes and one more, "other", for a cause the tree does not hold. Each observation says one cause's condition was seen or not, with the proof that saw it, and Bayes' rule takes it in for every cause at once: the cause it speaks to shows the condition with that proof's sensitivity, and every other cause shows it only as often as the condition turns up where it is not the cause. A model's reading enters as soft evidence at its calibrated probability, never as a verdict. Each proof's sensitivity and each condition's prevalence is a stated assumption until the learning loop measures it.

The next check is chosen by expected information per unit of cost: the bits it should take off the belief's entropy, averaged over every outcome it could have, divided by what running it costs (already in the capture, an agent's run, a paste, or a question only the engineer can answer). A belief is settled when one cause alone holds 1 − α of it. Even then, a root-cause gate in code must see a real proof before the cause is confirmed: a native tool's own answer, a correlation over a window, a control that differs only in the suspect, or a before and after watched for the fault's natural period. Otherwise the cause stays probable, and says so. Two or more hosts showing a symptom in the same second test what they share first, with each host's own restart window left out. Across nine diagnoses kept on one record, this weighed 45 candidate causes and confirmed two; six diagnoses settled and three were held for the engineer.

9.9 The fix list, and a small model made honest

Work units that hold still. Asked to group findings into work, a frontier model gives a slightly different grouping every time: of pairs it ever put together, it kept only 53% to 87% together across runs. That is useless for tracking work. So the model writes each client's catalogue of fixes once, each fix one change done once with what it changes and what it prevents, and every finding is then placed into the one fix that clears it, or none. On placement the same model agrees with itself 97.5% to 100% of the time. "None" grows the catalogue.

Placement is the small model's seat. Each new finding is offered the six fixes nearest its words, and the calibrated decision model chooses. That is cheaper and faster than a frontier call, and it is only acceptable because of what stands between its answer and any use of it.

The decision model ranks well and reads wrong. Measured: answers it stated as 91.4% sure were right 76.1% of the time. Thresholds set by eye on such numbers missed their own risk targets by 7.5 to 12.5 points. So its confidence is never used raw:

  1. Recalibration. Per question, on labelled answers, by isotonic regression: a monotone map from what it says to how often it is right.
  2. Acceptance within a stated error bound. An answer is accepted only at or above the lowest calibrated confidence at which a one-sided Clopper-Pearson bound on the error rate of the labelled answers above it stays under the action's limit. Candidate thresholds are tested from the most confident down, stopping at the first that fails, so the bound holds as stated without a correction for multiple testing. In practice: with no errors observed, 59 labels are needed to bound error at 5%, and 149 to bound it at 2%. An action that touches a server gets a smaller limit than a note.
  3. Consistency probes. A choice asked again with its options reversed, a yes asked as its negation, a question asked again in other words, all in the same request. When a probe disagrees, the answer climbs whatever its confidence.
  4. A shadow week. A new threshold decides nothing for its first seven days. Every answer in that week is recorded beside what actually happened.
  5. A pinned version. Thresholds are fitted to one model version. A request names that version exactly, and an answer from any other version is refused, not used.

Anything below the line climbs to the frontier model, whose placement becomes the label that fits next week's line. Until an office has enough labels of its own, every placement is the frontier model's. And one rule is written on purpose: an engineer's own placement is never moved by a model.

What the decision model is never asked. To count, to read a date or a time window, to read a hex code, or to make the decision itself. It answers narrow typed questions (18 in the catalogue, plus three batteries) as a choice among named options, a score on a ladder, or yes or no with a probability. The model judges; code decides.

The line. A client's open fixes are then ordered the way an engineer would work them: the root before its symptoms; shared foundations before what leans on them (time, then DNS, then Kerberos and the directory, then logons, because Kerberos needs time and names and every logon needs Kerberos); a server others lean on before the servers that lean on it; read-only and reversible before risky; one change per server at a time; identical fixes grouped behind one gate with the first server as the canary.

9.10 A fix, written whole

A fix is written only when what it would settle is settled, and code decides that on typed fields, never on words. Then the frontier model writes it whole:

Part What it is
The pre-check A read-only test that is true while the problem exists. It is the problem's fingerprint, run first to confirm the change is still needed, and run again afterwards as proof
The change What to change and where, as a script with its guards: the right machine, a dry run by default
The proof What output shows it worked
The way back How to undo it

Replayed against 72 past diagnoses, the model wrote the engineer's own fix, or part of it, 86% of the time, and every one came with a pre-check, a proof and a way back.

Two further properties are worth stating plainly.

"No change worth making" is a good answer. The model decides first whether a change is worth making at all. If not, the fix is kept as left, with who it rests with and why, and nothing waits at a gate. In the worked run, the watch declined to write a fix that would have set DNS to secure updates before the time fault was repaired, with the reason that doing so in that order would cause an outage. A system that can decline is a system you can leave running.

The gate is a person. The fix waits on a page that shows its four parts, with Approve and Not now. An office can require two engineers. With "changes to servers" off, which is the default, an approved fix is handed to the engineer with its script to run. With it on, the approved script goes to that server's agent with its digest, the agent runs it only if the digest matches, and a client's fixes go in waves: the canary first, each next server only after the one before came back healthy, one fix per client out at a time, nothing during quiet hours. A result that is not healthy stops that client's wave until an engineer takes it up. An engineer can grant a class of reversible fix leave to run alone for one client; a risky fix, or one made by hand, always waits.

Then the proof of section 8.6: a measurement taken later, from outside the change, against a control.

9.11 The reader of names

Free text is full of things worth extracting: a host nobody has recorded, an account, a service, a product. The approach is code first and a small local model second.

Code reads everything that has an exact shape, exactly: IP addresses, Windows error codes, security identifiers, UNC and registry paths, URLs, accounts. It also reads every name the record already knows wherever it stands as a whole token. Measured on 61 real engineering texts, hosts and services read this way came back at 100% precision with every known one found. A known name that is also a common word (a machine called DNS) is held, because code cannot tell it from the word.

GLiNER 2.5 reads what has no shape. It runs in its own process, below normal priority, with no window and no port, on the server's own processor, so nothing leaves the building. Its raw spans are weak: host precision was 6% to 7% zero-shot on those same texts. So a span from it is never acted on. It proposes; the frontier model confirms during filing; and each confirmation is a label. On one real filing it proposed 60 names and the frontier model held 8 of them as right, which is exactly why it proposes and does not decide. Every week the trust given to it, per kind of name, is fitted again from those labels.

Using a weak model honestly is a design skill. The wrong conclusion from "7% precision" is to remove it. The right one is to give it a seat where a wrong answer costs nothing and a right one saves a frontier call.

9.12 Talking to the work

The console is how an engineer talks to a Job. A question is routed by code before any model sees it:

  1. A fact the record holds (a server's last boot, its roles, a client's open Jobs, a firewall's firmware) is answered from the database, dated, with no model call. Facts from the record are exact.
  2. A concept is described by the cheaper model, which is held to describing: no machine's evidence, no cause, no script. A cheaper model may describe and never diagnose.
  3. Anything else is a turn of the frontier model on that Job, with the Job's history, the server's capture and a small set of tools.

Every line an answer quotes is checked, word for word, against what the turn was shown. An attached log is read by code first: kept whole when it fits, otherwise each repeated line kept once and counted, with the lines that matter first. A steer typed while a check is out reaches the next look. Web search is off for every question until the engineer turns it on for that one, and then it is its own call that sees only the question's words with every client, machine and domain name replaced by a stand-in: no capture, no history, so no query can carry a name.

The Job's documents, held to its facts

A Job's time entry, the client email and a remediation report are written from the Job's own record of facts, in the office's own shapes, and nothing is sent from the application. Since v9.0.2 each is held to those facts the way the audits' words are (section 9.14). Every number, in figures or in words, every address and every quoted name must be in the Job's facts. Every machine the record knows by a name with a digit or a hyphen (191 of the 206 in the estate it was built against; a plain word could be a word) must be one this Job names. Nothing may name this application, a model or an AI. A document that fails is asked for once more, with what was wrong. One that still fails is kept, with a note above it naming what the record does not hold, so the engineer sees it before copying it.

A Job's report no longer writes its own list of findings: its printed page carries the record's own issues and where each stands. What waits on the client is scoped to the Job's own servers: its own approvals, and the client's questions traced through typed links to the server whose read raised them. Measured over the real model's kept documents before it shipped, the check flagged two true statements, and both were put right at their source; what it still flags is true: an estimate nothing in the record holds, and a count of open issues one short of the record's.

9.13 Checks the model writes

When a read finds something no deterministic check raises, the product can turn the finding into one. The model writes it as a rule: one kind of record, conditions on its fields, the kind of machine it applies to, and a sentence to say. The rule is interpreted, never executed: code evaluates the conditions against each server's parsed record. It is kept only if it fires on the finding's own server. A silent rule is shown that server's rows once and repaired; one still silent is dropped with the reason and never asked again. A rule that fires waits for an engineer to confirm it, with every server it fires on listed, before it joins the floor. Absence is not a value: only "exists" may speak of a field that is not there.

9.14 The audits' words

The site audit and the firewall audit are written by the model and are still safe to hand a client, because of one arrangement: the model is given the audit's facts and nothing else, and it never supplies a fact.

Code lays out the whole audit first: every finding, table, figure and count. The model writes the prose that walks a reader through it: the dominant risk, why each first action comes where it does, each chapter's takeaway, each finding's claim. Then code reads every field before it is used. Each number, whether written in figures or in words, each IP address and each quoted name must be in the facts. Nothing may name this application, an AI, or a framework the audit does not judge. A field that fails is asked for once more with what was wrong. One that fails again is dropped and the audit prints its own deterministic sentence in that place.

On the release candidate, with the real model: a firewall picked at random, 13 of 13 areas and 182 of 182 fields kept; a 23-server fleet, 11 of 11 areas and 136 of 136 fields kept. On the way there, three numbers the model wrote that were not in the facts were refused by code and rewritten on the second asking.

With the AI off, both audits still render complete, in code's own words. The model improves the reading; it is never load-bearing.

9.15 Learning from the work

Nothing asks an engineer to grade anything. Labels come from what the work already leaves behind, read by code:

  • A cause the loop confirmed is right when its fix proved: the issue closed as fixed, and every symptom that waited on it stayed quiet for the watch's period or was absent from a capture taken after the fix. It is wrong when an engineer closed the issue as "checked, not a problem", or the symptom came back.
  • The frontier model's placement of a finding labels the decision model's placement of the same finding.
  • The frontier model's verdict on a proposed name labels the local model's proposal.

Once a week, in code only, with no model call:

  • Each decision-model question with enough two-sided labels has its threshold refitted, and only when the new fit rests on at least as many labels as the one in force, so a handful of labels never replaces a well-founded line.
  • Each kind of run is measured from its graphs: which rung settled what, every answer whose outcome is known, with an error bound.
  • Alarms are raised with their reasons: accepted answers wrong more often than the bound allows, the share accepted drifting, a new model version answering with no fit, settled causes wrong more often than the loop's own bar.
  • A cause proved on three or more servers is proposed as a new check.

One figure should rise week on week: the share of questions settled below the frontier model. That is what "learning" means here, with a number on it.

Accuracy is always three numbers, never one: precision (of the answers asserted and graded, the share right, with an exact one-sided bound on the error rate so a high figure is never claimed from a handful), coverage, and cost.

9.16 Privacy and untrusted input

  • A capture is untrusted input. Share descriptions, account names and event text can carry instructions aimed at a model. The defense is structural: nothing acts on model prose, the gate hook never sees model reasoning, and every claim is checked against evidence the model did not write.
  • The name map. For any hosted model outside the primary provider, code replaces every client, host, domain and user name with a typed, stable stand-in. The map is built from the office's own records, never discovered by a model, and nothing goes out while a leak check finds a known name in the text.
  • No person is named. Product text and prompts say "the engineer". A capture's only trace of a person is an account, and the one shape that turns an account into a person is rewritten before the model sees it.
  • Credentials are scrubbed from any string bound for a log, a page or a stored record. Keys are encrypted at rest and never returned once saved.
  • The local model stays local. It opens no port and reads nothing but what it is handed.

11.2 Design law

The console follows a written style law that a lint enforces, and the law is mostly a list of refusals:

  • No containers. A section is one hairline, not a box. Decisions, issues, Jobs and fixes are rows, not cards.
  • State rides one edge. A thin rule at the left: gold for a decision, a live color for an answer, the severity ramp for a finding. Never a fill.
  • One framed button per surface. Everything else is a label. If every button is primary, none is.
  • Figures are written, not dialed. "11 being worked and 23 proved this week", not a row of gauges.
  • Names, evidence and figures in a monospaced face; every other word in one sans-serif. Nothing under 11 pixels.
  • Absence is said. "Not determined", with the reason, never a zero and never a blank.
  • Never explain the platform to its operator. A sentence that would still be true on a different product is cut. Every finding is the named entity, why it is true from its own evidence, and something to approve or open.

  • Every section is on a ledger. When the audits were rebuilt in v9's engine, each section of the earlier reports became a ledger row, and a test holds the rendered audit to every one of them. Nothing was quietly dropped in a rewrite.

A second audit of the same device knows the first. Each finding carries an identity that survives between runs, so it is matched to itself and not to its place in a list, and one that disappeared is classified by why.

13Operating it

A tool an office depends on has to be installed, signed in to, backed up, monitored and supported by people who did not write it. This section is the systems administration around the software.

13.1 Install

The release is one zip: the program's folder, its libraries, the local model and an install script. On a server:

  1. Unzip it.
  2. Run the install script as an administrator, or as SYSTEM from the remote monitoring tool. A -Plan switch prints what it would do and changes nothing.
  3. The script puts the data folder under the machine's program-data directory, readable by SYSTEM and Administrators only; registers a task that runs the program as SYSTEM after every boot and restarts it if it stops; opens the host firewall for the console's port and the agents' port from private addresses only; starts the program; and says whether both ports answer. Everything it says is kept in a log beside the program.

Upgrading is: remove the task, replace the folder, run the script again. The data stays where it is.

A start that fails still says why. The application's log lives in its data folder. If that folder cannot be used, the process would end before any log exists, and as a SYSTEM task it has no window to say so. So the entry point hands a failed start to one file beside the program. Once software runs on someone else's server, the logs they can send you are the only way you will ever read it.

13.2 People and access

  • Sign-in by name. Each engineer has their own password, kept only as a PBKDF2 hash. A wrong name costs the same work as a wrong password. An account rests for five minutes after five wrong tries, and one address may try twenty times in five minutes.
  • Attribution everywhere. Every write is stamped with the engineer who made it. Every approval is recorded with who gave it.
  • Two-person approval where an office asks for it.
  • The AI's switches. One master switch; under it, each AI function and each client. An engineer can hold one client's checks for a press, or turn the AI off for one client entirely. A setting that cannot be read is off.

13.3 Backup and recovery

Every client, capture, firewall, Job and its history live in one database file. A checked copy is made every night with SQLite's online backup, each copy is opened and verified, and the newest ten are kept. Office can name a second folder, on another disk or another machine, and proves it by copying the newest backup there at once. Restoring is stopping the program, replacing one file and starting it again.

13.4 Support

When something goes wrong, an engineer saves a support file from Office: one zip with the log's last 5 MB, the trail of screens that browser visited, the version and the machine, the agents' side of things, a failed start if there was one, and the records of any Jobs the engineer ticks. Every secret the application holds is scrubbed from all of it. The log, the screen trail and the model calls carry the same action ID, so the three line up into one story.

15How it was built

I built NinjaToolKit with Claude as an engineering partner, and the way that partnership is run is as much a part of the work as the code. It is the same problem the product solves, pointed at software instead of servers: get a frontier model to do a large volume of reliable work, and keep a person in control of everything that cannot be undone.

What I own. The architecture, the domain judgment, the safety model and the invariants, and every decision that cannot be reversed: a merge, a tag, a release, a change to a prompt, a paid call.

The process.

  • A plan before building. Every phase starts as a written plan that I approve, with the effects an engineer will see named in advance. Work outside an approved plan does not happen.
  • A durable project record. The position, my standing rulings and the design law live in the repository, not in a conversation, so decisions survive context limits and model changes. 111 numbered decisions; 38 research files.
  • Every outside fact is fetched again before it enters code. A version, an API's shape, a limit or a price is read from its source on the day it is used, pinned, and the read is named in the commit.
  • Ledgers move in the same commit as the code. A finding is marked fixed in the commit that fixes it. There is never a follow-up commit "for the record".
  • Done means walked. A green test is not done. Done is the built program, from an empty folder, with real input, pictured, and the picture read.
  • Zero-cost AI testing first. Every AI path is proved against a local stand-in before a real call is made, and no spend gate is ever proved by spending.
  • Human gates on irreversible actions. A push to the release branch is refused by the repository itself; at a release I run that one command by hand.
  • Measured, never recalled. Every number in a status report, a release note or this document is the output of a command run at the time.

Why it matters for the work I do. A forward deployed engineer's job is to take frontier models into a real operating environment and make them produce reliable work there. This platform is that problem at small scale: an environment with real constraints, real clients and real cost, where a model's output has to be held to evidence by code, and a person has to stay in control of everything that touches production.

18Lessons

  1. Let the strongest model see everything, and trust nothing it says. Filtering a frontier model's input to save money made it worse at exactly the thing it is best at. The savings belong after the read, in verification and placement, where small models and code are measurably right.
  2. Free prose and typed records need a bridge, and the bridge should be boring. Filing adds nothing and judges nothing. That is what makes everything after it checkable.
  3. A model that may only speak when certain goes quiet where a hypothesis is most valuable. Ask for a best read every turn and a statement of how settled it is. Then let "settled" open a gate and "likely" produce the next check.
  4. A safety control must be in the path, not in the prompt. The gate is a table in code. The model's reasoning never reaches it. Whether a person is asked is never a question put to a model.
  5. A small model's confidence is a ranking, not a probability. Recalibrate it on labels, accept it only inside a stated error bound, run it in shadow first, pin its version, and let it climb when in doubt.
  6. Measure the instrument before you trust the reading. An event log that holds four hours cannot tell you about a week. A field that always moves is not a change. A firewall address that looks public may be inside.
  7. Absence is not zero, and gone is not fixed. Most false reassurance in operations tooling comes from breaking one of those two rules.
  8. Prove a fix from outside the fix. A script that checks its own work proves that the script ran. The proof is a later measurement, by a different path, against servers nobody touched.
  9. Run the real thing, for real, before anyone else does. Four defects survived the 6,092 tests of v9.0.0 and were found in two evenings of using the product the way it is meant to be used.
  10. Make structure a ratchet. Rules that live in a document decay. Rules that live in a test that may only count down do not.
  11. Measure coverage; never assume it. "The export is read in full" was a belief until a tool traced the program's own code over every element path of 54 exports and found 341 of 1,923 read. The next day every one was accounted for, and the figure is now a ledger that tests read, not a sentence anyone has to remember.
